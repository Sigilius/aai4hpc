TODO 4 — A1 EXPECTED REPRODUCTION TIME
--------------------------------------------------------------------------------

Artifact Setup: 10-15 min. Cloning the repository and installing pinned
dependencies takes ~2 min (`make setup`). The remainder is materialising the
DuckDB view over the F-data parquet export, which is a one-line view creation
rather than a load — DuckDB reads the parquet files in place — so the cost is
disk residency of the export (~26 GB), not import time.

Artifact Execution: <1 min. The 119 fact-checkers and 25 trap-checkers are
string and numeric comparisons over already-logged answers; no LLM calls are
involved. Scoring all five configurations end to end took 34 s wall-clock.

Artifact Analysis: <1 min. Aggregating per-query scores into the FR/UAA tables
is pure arithmetic (`make tables`).

TODO 9 — A2 HARDWARE
--------------------------------------------------------------------------------

No specific machine or cluster node is required, and none of the reported
results depend on the orchestration host.

The experiments ran on a commodity Linux workstation (x86-64, Linux 6.8,
Python 3.10.12) with no GPU — the code sets CUDA_VISIBLE_DEVICES="" explicitly.
All model inference happens at a hosted API endpoint; local computation is
limited to DuckDB aggregation over the parquet export and LightGBM inference for
PAAgent, both CPU-only. Requirements are sufficient disk for the F-data export
(~26 GB) plus ~570 MB for the predictor artifacts, and ordinary network access.

Wall-clock timings will vary with API latency and rate limits, not with the
orchestration host.

TODO 10 — MODEL SNAPSHOT VERSION                       [NEEDS AUTHOR INPUT]
--------------------------------------------------------------------------------

Confirmed: the codebase pins no dated snapshot. config.py sets MODEL = "gpt-4o"
and every call passes that bare alias to an Azure AI Foundry project endpoint.
The served snapshot is a property of the Azure deployment, not of the code, so
it cannot be recovered from the artifact.

Retrieve it from the Azure portal — the deployment's "Model version" field for
the gpt-4o deployment used (e.g. 2024-08-06) — and record it here together with
the date range over which the runs executed. State plainly that the alias alone
does not pin behaviour and that results may shift if the underlying snapshot is
updated.

Two model tiers are used and both need recording. Structured MAS routes ~77% of
its calls (709 of 921 in one measured run) to gpt-4o-mini for extraction and
delegation gates, reserving gpt-4o for SQL generation, documentation synthesis
and final synthesis. The reported Structured MAS configuration overrides this so
that every call uses gpt-4o (MAS_FORCE_MODEL=gpt-4o, set in the Makefile). The
baselines are single-tier gpt-4o throughout. Reviewers who omit that flag will
reproduce a different, cheaper configuration.

TODO 17 — 3.1 A1 ARTIFACT EXECUTION (literal commands)
--------------------------------------------------------------------------------

  python3 score_run.py logs/metered_mas.log "Structured MAS" \
          results/json/mas.json --mas

Runs all 119 fact-checkers and 25 trap-checkers against one configuration's
logged answers and writes the scored JSON. --mas additionally retains the
dialogue-act trace, which only the typed configuration emits.

  make score

Does the same for all five configurations at once, reading the standard log
names and writing results/json/.

Each checker extracts a numeric value or categorical string from the free-text
answer and compares it to database-derived ground truth within a fixed
tolerance (±5-10% relative for failure rates, ±20% for energy, exact match for
categorical conclusions). Trap checkers award a point only for an explicit
refusal, and award zero if any value for the absent quantity appears.

--------------------------------------------------------------------------------
TODO 18 — 3.1 A1 ARTIFACT ANALYSIS (what the reviewer should see)
--------------------------------------------------------------------------------

score_run.py prints a per-configuration summary and writes per-fact and
per-trap scores into results/json/<config>.json. The aggregate block of that
file should match the corresponding row of Table III to within rounding.

Scoring the bundled reference logs must reproduce the paper's numbers exactly,
since the checkers are deterministic and the answers are fixed. Any discrepancy
indicates a checker or environment problem, not sampling variance.

One implementation detail a reviewer may notice: score_query() calls unwrap()
before matching. Answers are printed through textwrap.fill(..., 72), and the
checkers match literal phrases, so a refusal that happens to wrap mid-phrase
("...is not\navailable in the dataset") scored zero before this was corrected.
The bias only ever converted correct answers into misses.

TODO 21 — 3.2 A2 ARTIFACT ANALYSIS (where logs land, how to spot-check)
--------------------------------------------------------------------------------

Each run writes two files:
  logs/metered_<config>.log      full transcript: query, agent messages, answer,
                                 per-query wall-clock
  logs/usage_<config>.jsonl      per query: LLM calls, tokens (prompt,
                                 completion, total), turns, model mix

Spot-checks against the paper's qualitative claims:

  N46 (institutional affiliation trap) — Structured MAS refuses explicitly
  ("The Fugaku dataset does not contain information about user affiliations")
  while recovering both facts. Single Agent hedges or omits rather than
  refusing.

  N52 (core-hour billing trap) — Structured MAS recovers usr_2111's 2.26%
  failure rate and refuses the billing sub-question. Unstructured MAS drifts the
  rate under free-text relay and fabricates a core-hour figure.

  Grep the model mix to confirm the tier override took effect:
    python3 -c "import json,collections; c=collections.Counter(); \
    [c.update(json.loads(l)['models']) for l in open('logs/usage_mas.jsonl')]; \
    print(c)"
  With MAS_FORCE_MODEL=gpt-4o this prints gpt-4o only. Any gpt-4o-mini entries
  mean the flag was not applied.

TODO 24 — 3.3 A3 ARTIFACT ANALYSIS (expected numbers and tolerance)
--------------------------------------------------------------------------------

Scoring the bundled reference logs reproduces these exactly — the checkers are
deterministic and the answers are fixed, so there is no tolerance to allow:

  Configuration              FR                UAA
  Structured MAS             78.2% (93/119)    92.0% (23/25)
  Unstructured MAS           60.5% (72/119)    80.0% (20/25)
  Blackboard MAS             36.1% (43/119)    60.0% (15/25)
  Unstr.-Blackboard MAS      45.4% (54/119)    72.0% (18/25)
  Single Agent               84.9% (101/119)   32.0% (8/25)

Cost ratios, Structured MAS against Single Agent:
  tokens   2.52x     (33,137 vs 13,135 per query)
  calls    6.61x     (20.9 vs 3.2 per query)
  latency  3.43x     (23.7 s vs 6.9 s median)
  Blackboard MAS runs at 45% of Single Agent's token cost while declining more
  unanswerable sub-questions (15/25 against 8/25).

FROM FRESHLY GENERATED LOGS, expect variation. Across repeated Structured MAS
runs of identical code we measured FR spanning 82-93 of 119 and UAA 22-23 of 25.
A single fresh run is one sample: for any comparison turning on a few facts or
traps, run three times and report a mean with the spread. The qualitative
claims — Single Agent highest on FR and lowest on UAA, Structured MAS highest on
UAA, both blackboard configurations Pareto-dominated by Structured MAS — held
across every run we performed.
